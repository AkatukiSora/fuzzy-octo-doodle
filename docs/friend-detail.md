# フレンド詳細

`/friends/[friendId]` はフレンド一覧が返す実際のユーザーUUIDを使用する。
旧モックの `/friends/1` は実在ユーザーへ割り当てず、閲覧不可として表示する。

## 追加API

既存の `GET /api/friends/:userId` とブロックAPIは変更していない。

### GET /api/friends/:userId/activity

成立済みフレンドだけにプロフィール、統計、タスクページを返す。
自分、未承認、解除済み、双方いずれかのブロック状態、無関係な相手は404。

- `sort`: `soonest`（既定）または`latest`。現在の状態で適用される期限とIDでソートする。
- `limit`: 1〜50（既定20）。`cursor` に前ページの `tasks.nextCursor` を渡す。
- 一覧には挑戦中、審査中、追加提出待ち、未達成を含む。
- 適用期限 `dueAt` は審査中なら審査期限、追加提出待ちなら追加提出期限、それ以外は元の期限。
- 達成率は既存の `successRate` 関数を利用。達成÷（達成＋未達成）で、判定不能を除外する。分母0ならnull。
- 進行中は期限内の挑戦中・追加提出待ちと、審査中。期限切れは未達成、提出期限を過ぎた挑戦中・追加提出待ち。審査待ちを提出期限切れには数えない。
- 金額非公開のタスクも内容は表示する。既存の `toTaskView(task, "friend")` により `penaltyAmount` は返さない。

### POST /api/friends/:userId/report

成立済みフレンドへの通報を保存する。認証・Originガードは既存の構成を使用する。

- `Idempotency-Key`: UUID、必須。
- 本文: `{ "reason": "spam", "detail": "理由" }`。
- 理由は `harassment`、`spam`、`inappropriate`、`other`。詳細は1000文字以内で、`other` の場合は空白だけの内容も不可。
- 成功は201と `{ id, createdAt }`。通報内容を対象者へ通知する処理はない。
- `(reporter_id, idempotency_key)` を一意にし、savepointを使う既存ヘルパーで競合を処理する。同時送信・再送では同じ受付結果を返す。別内容へのキー再利用は409。
- 本人の保存済み通報の再送は、ブロック後でも元の受付結果を返す。新規通報はフレンド権限を要求する。

## DBとブロック

`0002_user_reports.sql` で通報用テーブルを1つ追加する。既存テーブルの変更はない。
デプロイ時は通常のAtlasマイグレーションをAPIの起動前に実行する。

ブロックは既存の `POST /api/users/:userId/block`、解除は同じパスの `DELETE` を使用する。
ブロック後はプロフィール・統計・タスクを画面から除去する。
再読込時は `GET /api/blocked-users` で本人が設定したブロックだけを確認し、解除操作を表示する。
解除しても既存のドメイン仕様どおり関係はremovedとなり、再申請・承認が必要。

## ローカル確認

フロント・API・PostgreSQLを起動し、既存の `DEV_AUTH_USER_ID` を使う2つのAPIインスタンスで検証した。
本番用セッション認証のログイン処理は既存の未実装範囲であり、この変更には含めない。

1. 専用確認ユーザーに状態・期限の異なる実DBのタスクを用意し、達成率50%、進行中3件、期限切れ2件を確認。
2. 金額非公開タスクの内容表示・金額の不在、両方向の期限順ソート、limit=2での全ページ取得、不正なクエリの400を確認。
3. 同一キーで3件同時に通報し、同じ受付IDと実DBの1レコードを確認。別内容のキー再利用は409。
4. ブラウザから通報理由・詳細を入力し、連続クリックしても実DBの保存は1件であることを確認。
5. ブロックのキャンセル・実行・再読込・解除を確認。ブロック中は双方の詳細APIとタスク直接取得が404になり、フレンド一覧からも消えることを確認。
6. PC・モバイル（1440、768、390、320px）で表示と操作を確認。
