# 決済関連画面（PAYMENT-01〜04）

## 画面と現在の提供範囲

- `/mypage/payments`：マイページから開く決済履歴。支払い方法、3種類のフィルター、履歴カード、空状態を実装。
- `/mypage/payments/[paymentId]`：対象タスク、タスク状態、金額、決済状態、請求情報、支払い方法、操作欄を実装。
- `/mypage/payments/[paymentId]/inquiry`：請求概要、理由4択、詳細説明、画像選択・プレビュー・削除、バリデーションを実装。
- `/mypage/payments/inquiries/[inquiryId]`：問い合わせ概要、対応状態、記録済みイベントだけのタイムライン、マイページへの導線を実装。

既存の ProfilePageLayout / AppLayout / Button / Badge / EmptyState / TaskStatusBadge を再利用。請求カード、決済バッジ、問い合わせバッジ、支払い方法、エラー表示も共通化している。

## バックエンド調査と制約

`backend/src/application/ports/payment-gateway.port.ts` はタスク作成前の確認と請求依頼だけを定義し、PersistenceModule は MockPaymentGateway を使用している。モックは支払い条件を常に許可し、請求をログに出すだけで、実際の決済はしない。

既存の controller、DB 型定義 (`backend/src/infrastructure/db/schema.ts`)、SQL マイグレーションに、決済履歴、登録済み支払い方法、請求問い合わせの管理・参照実装はない。task_objections はタスク審査への異議であり、請求問い合わせとして流用しない。

`frontend/src/lib/paymentApi.ts` の PaymentReader は接続境界であり、現在すべて `unavailable` を返す。未実装のURLには通信しない。実データの代わりにサンプル履歴、カード番号、問い合わせ番号や日時を表示しない。画面は取得準備中を表示し、空の取得結果と区別する。

支払い方法の変更、支払い再試行、問い合わせ送信は常に無効。フォームの入力・画像選択は画面内の確認のみで、通信・永続化・問い合わせ番号の採番・送信完了画面への遷移は行わない。画像はJPEG/PNG/WebPを最大3枚、詳細説明は空白だけを除いて1〜1000文字（Unicodeコードポイント単位）。

## 状態の意味

- 決済状態：未払い / 決済処理中 / 支払い完了 / 決済失敗 / 請求取消。
- 問い合わせ状態：受付済み / 調査中 / 回答済み / 対応完了。決済状態とは別データ・別バッジで表示。
- 完了フィルターは支払い完了だけ。未完了は未払い・決済処理中・決済失敗。請求取消は「すべて」でのみ表示し、支払い完了として数えない。
- タスク状態は実際のタスク状態を表示し、決済状態から推測・変更しない。
- タイムラインは取得したイベントだけを表示。未記録の進捗、予定段階や日時を生成しない。
- 日時表示は日本時間。画像設計の「調査中」を決済状態として扱う点は、上の独立した問い合わせ表示に調整した。

## ID・障害の扱い

未接続の現段階ではIDの存在を判定できないため、任意のIDを有効な決済・問い合わせとして表示しない。取得できない旨と履歴への戻り先を表示する。存在しないことをAPIで確認できていないIDを404として断定しない。

接続後、存在しないIDは `not-found` とし、Next.js の `notFound()` と決済専用の404画面で扱う。通信障害は `error` として表示し、履歴0件や未登録と混同しない。予期しない例外には再読み込み可能な error boundary を用意している。

## 今後必要なバックエンド実装

1. 認証・所有権検証付きの決済履歴/詳細と支払い方法の参照API。決済専用の永続化と状態、金額・日時・請求理由の正式なレスポンス契約。
2. 実決済サービスとの連携、結果通知による状態更新、安全で冪等な再試行API、支払い方法登録・変更フロー。
3. 請求問い合わせの作成・参照API、添付画像アップロード、問い合わせ状態と対応履歴の保存・運営側の更新処理。
4. PaymentReader で認証付き参照とレスポンス検証を実装。404/認証エラー/障害を区別し、送信の正式な契約ができた段階で入力フォームと接続する。

この変更では、決済処理、請求処理、問い合わせ管理システムやDB/APIの追加・変更を行っていない。

- 全体 ESLint、フロントエンド/バックエンドの型チェック・ビルド。
- フロントエンド59テスト（フィルターの状態独立性、入力境界値、未実装APIの安全な結果、JST表示を含む）。

- 検証用データと一時的な画面は確認後に削除し、アプリには含めない。
